- **S1 — Pure date module.** Create `src/content/datestamp.ts` (imports only `type { Locale }` from
  `../i18n/config`) exporting:
  ```ts
  export type DateStampParts = { day: number; month: string };
  export function dateStampParts(publishedOn: string, locale: Locale): DateStampParts;
  ```
  `publishedOn` must match `/^(\d{4})-(\d{2})-(\d{2})$/`. Build `new Date(Date.UTC(year, month - 1, day))`;
  if the pattern does not match, or the date read back with `getUTCFullYear()`, `getUTCMonth()` and
  `getUTCDate()` differs from the three numbers (so `2026-02-30` is rejected), throw an `Error`.
  `day` is the day as a number (no leading zero). `month` is
  `new Intl.DateTimeFormat(locale, { month: locale === "ar" ? "long" : "short", timeZone: "UTC" })
  .format(date)`; the zone is fixed to `UTC` so the visitor's zone, the build machine's zone and the
  runtime clock never change the result. No month list, no catalogue key. Names must pass
  `guard:naming`.
- **S2 — Unit tests.** Create `src/content/datestamp.test.ts` with exactly three `it(` calls (Vitest,
  `describe("datestamp", …)`). Never write a literal month name: compute every expected month with

  1. `dateStampParts("2026-10-04", "en")` equals `{ day: 4, month: expectedMonth("en", 2026, 10) }`, and
     `dateStampParts("2026-09-21", "en")` has `day` 21.
  2. `dateStampParts("2026-10-04", "ar")` equals `{ day: 4, month: expectedMonth("ar", 2026, 10) }`; its
     `month` differs from the `en` month of the same date and contains no `[A-Za-z]` character.
  3. `dateStampParts("2026-12-31", "en").day` is 31 and `dateStampParts("2026-01-01", "en").day` is 1
